# 阶段 0 · 协议核实 — 执行方案

> 状态：待人工审核。审核通过前不执行任何实测。
> 工作目录：`temp/P0/`（本阶段一切脚本、记录、产出都在这里）。
> 一句话目标：摸清插件 ↔ 本地 `opencode serve`（v2.2.5）之间的全部"对话暗号"，写成阶段 1 的施工图纸 `protocol-notes.md`。

## 1. 硬约束

- 所有临时文件、探针脚本、实测记录只放 `temp/P0/`；不改 `temp/opencode-dev`、`temp/opencode2dsh-master` 任何文件。
- 源码只读；实测用最小请求；**不读取、不打印、不复制任何凭据值**（只确认机制与位置）。
- 实测会消耗真实账号额度并产生真实上游流量：对话类请求**总数 ≤ 10 次**，每次用极小 prompt（如"回复 ok"）；只读接口（列表/健康）也保持克制。
- serve 只绑 `127.0.0.1` + 随机端口；探针进程用完即杀，不留孤儿。
- 实测一旦撞限流/风控立即停止该项，记录现象，不重试轰炸。

## 2. 验证项（V1–V5）

### V1 · 五组接口的真实形状（核心）

- **要回答**：建会话、发消息、收事件（SSE）、列模型、审批（permission）各是什么方法/路径/请求体/响应体？错误长什么样？
- **源码线索（待核实）**：`opencode-dev/packages/protocol`（HttpApi 定义）、`packages/server`（路由实现）、`packages/sdk`（生成的客户端，可当接口索引用）。
- **实测方法**：起 serve 后用 Node 24 自带 fetch 写探针脚本逐个调用，记录原始请求/响应。
- **产出**：每组接口一份"源码出处（文件:行号）+ 实测样本"。
- **为什么**：参考插件是 v1 暗号，本机是 v2.2.5，必须以源码+实测双证为准。

### V2 · 凭据直接复用（命根子，优先验证）

- **要回答**：serve 启动后如何拾取本机 CLI 的现有登录？读哪个文件/数据库？`--pure` 等旗标会不会把登录隔离掉？共享数据目录有什么副作用？
- **源码线索**：`packages/core` 的认证/存储模块；`packages/cli` 的 serve 命令旗标定义；本机 `~/.local/share/opencode/`（已知有 opencode.db）。
- **实测方法**：用默认数据目录起 serve，调一个需要登录态的端点（如列模型/最小对话），确认"不登录第二遍就能用"。
- **产出**：凭据机制结论 + 推荐方案（预期：共享本机数据目录，插件会话出现在 CLI 历史里，视为调试特性）。
- **为什么**：此条不通，"不伪装复用本地"路线就要调整，所以排在实测第一位。

### V3 · 双入口并发模型

- **要回答**：多个 opencode 会话能否同时各跑各的回合、互不串话？同一会话重复发消息是排队还是拒绝？
- **源码线索**：`packages/core` 的 SessionExecution / SessionRunCoordinator（上游 AGENTS.md 称不同 Session 可并发，需证实）。
- **实测方法**：建 2 个会话，同时各发一条极小消息，观察响应是否独立、事件流是否按会话分开。
- **产出**：并发结论（可并行 / 需排队 / 其他），决定插件会话管理设计。
- **为什么**：双入口（DSH + 外部 API）必然并发，提前知道 CLI 的脾气。

### V4 · DSH 工具透传可行性

- **要回答**：v2 的消息接口能否携带客户端自定义工具定义？模型的 tool-call 能否经事件流传回？
- **源码线索**：`packages/protocol` 消息接口的请求 schema；`packages/core` 工具注册机制。
- **实测方法**：源码确认支持后，带一个无害假工具（如"获取当前时间"）发一次请求，看模型是否发起调用、事件形状如何。**源码不支持则不做实测**，直接记结论。
- **产出**：支持/不支持 + 证据；支持则给出透传设计要点，不支持则定案纯聊天。
- **为什么**：决定插件是纯聊天通道还是全功能通道；无论如何 CLI 原生工具先拦死。

### V5 · 健康检查与进程生命周期

- **要回答**：serve 启动后哪个端点表示 ready？版本怎么核对？启动耗时多少？被杀/崩溃时什么表现？
- **源码线索**：`packages/server` 的健康/全局端点；`packages/cli` serve 启动流程。
- **实测方法**：起 serve 时顺带记录（启动命令、旗标、端口、ready 信号、耗时）；最后 kill 一次观察退出行为。
- **产出**：进程看护参数表（启动命令、健康端点、ready 判据、回收方式）。
- **为什么**：插件要负责拉起和回收子进程，这是看护代码的输入。

## 3. 执行顺序

```
1. 源码摸底（protocol/server/sdk/core 相关部分）→ 接口候选清单
2. 写探针脚本（temp/P0/probe/，纯 Node fetch，零依赖）
3. 起 serve → 先验 V2（凭据）+ V5（健康），不通则停下向人工报告
4. V1 五接口逐个实测（含 1 次最小对话）
5. V3 并发实测（2 会话 × 1 条小消息）
6. V4 工具透传（源码先行，实测至多 1–2 次）
7. 汇总写 temp/P0/protocol-notes.md，清理探针进程
```

## 5. 总验收标准

- V1–V5 每项都有明确结论与证据；存疑项如实标注，不不懂装懂。
- 凭据直接复用被实测证实可行（或提出替代并说明理由）。
- 对话类实测请求总数 ≤ 10；无凭据值落盘；无孤儿进程；两份参考源码零改动。

## 6. 风险与应对

| 风险 | 应对 |
| --- | --- |
| serve 起不来或不认本机登录 | 记录现象回源码找注入机制；仍不通则停下报告人工，不硬试 |
| 实测撞限流/风控 | 立即停该项，记录现象，换时间或请示，不重试轰炸 |
| v2 API 与 v1 差异大 | 以源码+实测为准，参考实现仅作语义对照 |
| 额度消耗 | 对话请求 ≤10 次封顶，prompt 极小化 |
| 源码庞大迷失 | 以 protocol 定义和 sdk 生成客户端为索引入口，不全文通读 |
